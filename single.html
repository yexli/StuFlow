Vite 8 深度实测：Rolldown 原生打包到底快了多少？

2026-10-07 1.8k 阅读 58 评论 约 9 分钟 5,340 字

Vite 8 把打包内核从 Rollup（JS 实现）切换成了 Rolldown（Rust 实现），官方宣称构建速度提升「一个数量级」。数字很吓人，但落到我们自己的项目里到底能快多少？我把手头三个真实项目（一个组件库、一个中后台、一个博客主题）全部升上去跑了一轮完整压测，这篇文章就是那份原始数据的整理。

先说结论：冷启动从 9.4s 降到 0.7s，HMR 大项目里稳定在 100ms 以内，但 SSP（服务端渲染同构打包）阶段还有三个坑需要手动绕行。

—— 本文结论速览

测试环境与项目样本

为了保证数据可比，三个项目在同一台机器上各跑五轮取中位数，vite@5.4.8 与 vite@8.0.1 之间只升级 Vite 及配套插件，业务代码零改动。机器配置与项目规模如下：

项目类型模块数依赖数产物体积

冷启动：提升是量级的，但依赖规模

Rolldown 用 Rust 重写了模块解析与转换管线，收益最直接体现在冷启动上。三个项目的实测结果：

小项目（96 模块）从 1.2s 降到 0.28s，感知上就是「秒开」；中后台这种 1,700+ 模块的大工程才是重头戏——9.4s 直接打到了 0.7s，早上泡咖啡回来 dev server 已经跑起来的体验确实回不去了。

不过要注意一个细节：这个 0.7s 是「首次可交互」时间，不是完整依赖预构建（optimizeDeps）时间。首次访问某个冷门依赖时仍会触发按需预构建，页面会有一次短暂的可感知延迟，官方文档里称其为 deferred dependency optimization。

i
实践建议：如果你的项目用 monorepo 且依赖被多个包共享，把 optimizeDeps.include 显式列全，可以消除掉 90% 的按需预构建卡顿。

HMR：快到可以关掉进度提示

热更新是日常开发中感受最深的环节。改一个组件文件，Vite 5 在大项目里 HMR 回包普遍在 600~900ms（含浏览器重渲染），Vite 8 实测稳定在 100ms 以内，多数情况下是 40~70ms——快到你甚至可以把终端里的 rebuild 提示关掉。

bench/hmr.spec.ts 
// 压测脚本核心片段：连续修改组件并采样回包延迟
const samples = await bench({
  entry: 'src/views/dashboard/index.vue',
  edits: 50,        // 连续 50 次修改
  cooldown: 120,   // 每次间隔 120ms，模拟真实敲键盘节奏
});
console.table({
  p50: percentile(samples, 50),   // 46ms
  p95: percentile(samples, 95),   // 88ms
  p99: percentile(samples, 99),   // 103ms
});

产物体积：基本持平，个别场景反增

打包产物方面，三个项目总体持平（±2% 以内），但有一个反直觉的发现：使用了大量 dynamic import 的中后台项目，产物体积反而增加了 4.6%。原因是 Rolldown 的 chunk 划分算法比 Rollup 更激进，倾向合并共享 chunk，导致某些页面级 chunk 变大。对走 CDN 且开启 gzip 的场景影响很小，但如果你在做「首屏 KB 预算」就需要重新跑一遍数字。

!
注意：如果升级后构建报 ROLLDOWN_PLUGIN_API_MISMATCH，说明某个旧插件还在用 Rollup 的兼容层 API，去插件仓库找 8.x 适配版，别硬压版本号。

SSP 阶段的三个坑

同构打包（SSR + SPA 混合）是我这次升级翻车最狠的地方，三个坑按踩的先后顺序记录：

坑一：环境变量注入时序

Vite 8 把 import.meta.env 的替换从转换阶段挪到了生成阶段，导致原来在插件 transform 钩子里读 env 的写法拿到的是占位符。解法是改监听 generateBundle，或者直接把 env 读取挪到配置文件加载期。

坑二：CSS 模块命名不稳定

同一个 CSS Module 在 dev 与 build 下类名哈希算法不一致，SSR 注入的类名和客户端 hydration 对不上，页面直接裸奔。临时解法是锁定 generateScopedName 为固定模板。

坑三：插件并行化导致的隐式依赖顺序

Rolldown 默认并行执行插件钩子，两个有先后依赖的插件（比如先做国际化文案替换、再做压缩）在 Rollup 时代靠「注册顺序」隐式保证，现在必须显式声明依赖或者拆成两轮构建。

要不要现在就升级？

我的建议分三档：纯客户端 SPA，现在就升，收益立竿见影；组件库 / 工具库，等生态插件跟进一两个版本再上；重 SSP 的同构项目，先在分支上把第三节三个坑趟一遍，确认没有使用受影响的插件再合。
